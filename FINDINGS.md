# FINDINGS

Slot range: 439865000–439865999 (1,000 slots), ingested via Helius (ADR-0004, after the public mainnet-beta endpoint started throttling under cumulative session load — see ADR-0002).

## Ingestion: throughput, memory, and a real crash

Final successful run: **1000/1000 blocks, 0 skipped, 0 failed, no gaps**. 1,756,448 transactions, ~34.9M account_locks, ~4.0M token_balances, 15GB on disk. `PRAGMA integrity_check` clean.

Getting there was not clean. The first full-range attempt **crashed the machine** partway through (125/1000 blocks committed before the crash; WAL mode recovered that partial data with no corruption — `integrity_check: ok` on reboot, which is the WAL decision actually paying off, not just a theoretical benefit). Root cause: `writer.rs` was calling `.execute()` fresh for every row with no prepared-statement caching — tens of thousands of un-cached prepares per block made the writer the throughput bottleneck, which caused the bounded fetcher→parser channel (carrying raw, unparsed JSON, sometimes 20+MB per block) to fill and stay full, accumulating large blocks in memory faster than they could be drained.

Fix: `prepare_cached` for all writer statements, plus a much smaller dedicated bound on that specific channel (4, vs. 64 elsewhere) since it's the one carrying large payloads. Re-verified with active memory logging on a 200-slot test: memory grew ~1GB and *plateaued* instead of climbing, then dropped cleanly after the process exited. The full 1,000-slot rerun peaked at **~12.5GB used** (of 15GB system total), never dropping below ~3GB available — no swap, no crash.

Second real problem, same day: after fixing memory, a 200-slot test got only 20/200 blocks — 180 failed with HTTP 429, despite our own governor limiter correctly holding to 10 req/s. This was the public endpoint's own undocumented throttling reacting to cumulative session usage (many curl checks, several smoke tests, the crashed run — all from one IP). Switched to a Helius free-tier endpoint (ADR-0004); the full range then completed cleanly.

**What didn't work / lesson**: a schema gap surfaced twice, both times *after* a full ingestion was already done — first `tx_index` (needed for Part 2's scheduler to process transactions in original order, which the schema never captured), then native SOL balances (needed for full OHLCV price-pair coverage, also never captured). Both required either a targeted backfill (tx_index — lightweight, `getBlock` with `transactionDetails: signatures` instead of full payloads, a few minutes) or scoping the feature down (native SOL — a full re-fetch would have cost the same ~45–60 minutes as the original ingestion, so we scoped price inference to wrapped-SOL only instead and documented the gap, ADR-0008). The actual lesson: think through what every downstream stage needs from the schema *before* the first full ingestion, not after.

## Part 2 — Contention

Full-range greedy scheduling computation: **schedule depth min=22, max=1088, avg=264.3** steps per block; **step width max=1000, avg=6.6** transactions per step. Computing this over all 1,000 blocks took **11m23s** — genuinely CPU-heavy, which is exactly why it can't be computed live per API request (see Part 5) and directly motivated the async-starvation experiment.

Top contended account: one account accounts for ~24.9M write-conflict events and ~16.9M read-conflict events (schedule-derived counting, see ADR-0005) — almost certainly a high-traffic shared pool/vault account. Top "contended programs" are ComputeBudget and the System Program, but this is a real artifact worth calling out rather than a genuine insight: conflict events are attributed to *all* of a transaction's `program_ids`, and both of those programs appear in nearly every modern transaction (compute budget instructions are near-universal now), so they dominate the program ranking simply by ubiquity, not because they're inherently more contentious. The account-level ranking is the more meaningful one.

## Part 3 — OHLCV

Scoped to wrapped-SOL-paired trades only (native SOL was never captured — ADR-0008). Real yield on the full range: **66 candles (1m+5m combined) across 27 distinct mints** — low, and that's a genuine finding, not a bug, verified independently via raw SQL before accepting it: of 211,584 transactions touching both a WSOL leg and exactly one other mint, **211,390 (99.9%) net to exactly zero** token change when deltas are summed across all of that mint's accounts in the transaction — real SOL movement, no net token change, consistent with internal multi-account routing (vault patterns, intermediate transfers) rather than simple two-leg swaps. Of the remaining candidates, several were exact multiples of 1,000,000 token units — token-creation events (pump.fun's standard 1B initial supply) with an incidental SOL fee, not trades; filtered out.

Exclusions, all disclosed in the README: multi-hop routes (>1 non-WSOL mint touched), wrap/unwrap-only (0 non-WSOL mints), internal routing that nets to zero, same-direction deltas (incidentally also rejects simple two-sided liquidity add/remove), dust (<0.0001 SOL), round-number mint/creation amounts, tokens with no SOL pair (never produce a group at all), and native-SOL-denominated legs (untracked entirely).

## Part 4 — API and dashboard, bugs found

`/api/contention` cannot compute live (11m23s per request is unusable) — it serves a precomputed summary, built once by a separate `build_contention_summary` binary into dedicated `contention_blocks`/`contention_accounts`/`contention_programs` tables, same pattern as OHLCV candles.

Two real bugs found via actually loading the dashboard, not just reading the code:
1. `Math.max(...widths)` in `app.js`, spreading a **264,337-element** array (every step's width across 1,000 blocks) as function arguments — throws `RangeError: Maximum call stack size exceeded` in essentially all JS engines past ~65k–125k spread arguments. Silently broke the whole page once the contention summary finished computing and the dashboard tried to render it. Fixed with `reduce()`.
2. The dashboard defaulted to the highest-activity token (WSOL, by far) — which never has its own candles, since it's only ever the counter-leg, never the base token. Opened on a permanently empty chart. Fixed by sorting tokens-with-candles first in `/api/tokens`, and marking tokens with no matched trades in the dropdown label.

Also missing a viewport meta tag, which broke mobile layout (desktop-width rendering scaled down); added it plus a few responsive CSS rules (wrapping controls, horizontal-scroll containers for wide tables, stacked summary on narrow viewports).

## Part 5 — Load experiments

**Backpressure.** Policy: block (not shed, not buffer) — correctness matters more than throughput for a finite one-shot ingestion job, and bounded `tokio::mpsc` channels give this for free via `Sender::send().await`. Demonstrated on a 30-slot range, writer paused for 10s after the 5th block, with channel-capacity sampled every 200ms throughout. Result: `parsed_chan` (writer's immediate upstream, bound 64) drained from 64→40 free over the 10s pause (~24 items backed up, a real throughput data point: ~2.4 blocks/sec at that point in the run). `blocks_chan` (bound 4, further upstream) never saturated in this narrow window — the parser kept draining it fast enough that the full cascade never reached the fetcher stage within 30 slots / 10 seconds. Only a partial result, reported as such: the immediate-upstream mechanism is clearly demonstrated and matches expected `tokio::mpsc` semantics, but a longer pause or higher-volume range would be needed to see the cascade reach the fetcher. Resume verified clean: reran the identical range against the same DB, identical row counts both times, `integrity_check: ok`.

**Async starvation.** Ran the real contention-scheduling computation (limited to 100 blocks) two ways against a dedicated single-worker-thread server (`worker_threads = 1` — this dev machine has 12 cores, so the default multi-threaded runtime doesn't show meaningful starvation from one blocked thread; a constrained thread count is what makes the effect real and observable, and is itself a realistic scenario for small containers). Naive (computed inline in the async handler, no `spawn_blocking`): **1** `/api/tokens` ping got through during the entire ~50s computation, latency **50.24s** — completely blocked, queued behind the occupied worker thread for the whole duration. `spawn_blocking`, 54 samples: **min 203ms, p50 230ms, p95 301ms, p99 349ms, max 372ms, avg 246ms** — fully responsive throughout, no tail latency blowup. (Compute duration varies between runs — 50-70s across different passes, likely SQLite page-cache state — noted as a caveat, but the responsiveness gap itself is the real result and it's dramatic regardless of exact compute time.)

**Write-path contention.** Real 150-slot ingestion (active writer) with concurrent `/api/tokens` reads sampled every 200ms: 478 samples, min 7.4ms, avg 30.2ms, max 97.3ms, **zero** samples over 500ms, zero lock/busy errors in the server log. Idle baseline (100 reads, no concurrent writer, full 150-block DB): min 63ms, avg 73ms, max 115ms — actually *higher* than the during-write average. That's a confound, though, not a WAL effect: the during-write samples average over a *growing* table (0→150 blocks), while idle samples all hit the final, largest table size, so the raw averages aren't apples-to-apples. What actually answers the question is the *absence* of latency spikes or lock errors during concurrent writes — there were none. That absence is the real evidence WAL is doing its job here, more than the raw average comparison is.

Batch size / transaction boundary: one SQLite transaction per block (ADR-0003), chosen so a crash loses at most the one block in flight (idempotent re-fetch recovers it) rather than either paying an fsync per row or holding one long-lived write lock for an entire run.

## Performance profile

No `perf`/`cargo-flamegraph` on this machine (neither installed, and installing `perf` needs system package access not worth the risk this close to a deadline). Basic substitute: instrumented the two phases of the contention computation separately (`src/bin/profile_contention.rs`) — DB loading (`load_block_transactions`, two queries per block: transactions, then a join for account_locks) versus the scheduling computation itself (`schedule_block`).

Measured on 200 real blocks: **DB load 115.6s (81.6%), scheduling 26.0s (18.4%)**, total 141.6s (~708ms/block — consistent with the full 1,000-block run's 11m23s / ~683ms per block).

This corrects a wrong assumption: before actually profiling it, the guess was that the scheduler's `O(transactions × existing steps × locks per transaction)` structure was the bottleneck. It isn't — loading is. The real next step, if optimizing this further, is reducing round trips or indexing in `load_block_transactions`, not restructuring the greedy scheduler's data structures.
